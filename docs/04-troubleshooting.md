# 04. 트러블슈팅 · 튜닝

면접에서 가장 자주 묻는 "직접 겪은 문제와 해결 과정"을 정리했다. 각 사례는 **증상 → 원인 진단 → 조치 → 결과** 순서다.

---

## 1. Security Onion 패킷 누락 — 통합 솔루션을 걷어낸 결정

### 증상
Security Onion으로 관제 환경을 구축했는데, **탐지되어야 할 트래픽이 간헐적으로 잡히지 않았다.**

### 원인 진단
수집 계층과 후처리 계층을 나눠 실측했다.

- **수집 계층 (PF_RING)**: `tcpdump`로 캡처하면 패킷이 정상 수신되는데, 같은 순간 Snort3의 PCAP과 PF_RING 통계를 비교하니 **PF_RING이 간헐적으로 `Received: 0, Analyzed: 0`** → DAQ로 쓰인 PF_RING이 패킷을 흘리고 있었다.
- **후처리 계층 (Barnyard2)**: Snort2가 `snort.unified2.*`를 실시간으로 쌓는데 이를 넘겨받을 **Barnyard2 프로세스가 멈췄다.** 재기동하면 누적 스풀을 일괄 처리하며 **CPU 90%** 까지 치솟아 구조적으로 불안정.

### 조치
문제가 특정 룰이나 설정이 아니라 **아키텍처 양쪽(수집·후처리)에 걸쳐 있어**, Security Onion 의존을 걷어내고 **Snort3 + Python으로 수집·분석 파이프라인을 직접 구성**했다.
- 센서: `libpcap` 직접 캡처 + BPF 1차 필터 + Snort3 `alert_fast`
- 전송: 자체 바이너리 프로토콜 + Batch, 단절 시 재연결·재전송
- 분석: 중앙 서버에서 dpkt 파싱·재조립·판정 (센서-중앙 역할 분리)

### 결과 / 교훈
- 패킷 유실 없이 다중 IDS를 단일 서버에서 처리하는 구조 확보.
- **"통합 솔루션이라도 그대로 신뢰하지 않고 병목을 실측한다"** — 원인을 계층별로 좁혀 재현·측정한 뒤 대안을 선택한 경험.

## 2. Flow 포화 시 성능 병목 — 53.6배 개선

### 증상
동시 추적 Flow가 많아지면(2만 개 초과) 분석 처리량이 급감했다.

### 원인 진단
Flow를 조회·정리하는 로직이 **매 패킷마다 전체 Flow 테이블을 훑는 O(n) 전수 탐색** 구조여서, Flow 수가 늘수록 처리 비용이 선형으로 증가했다.

### 조치
Flow 탐색·만료 처리를 자료구조 기반으로 개선해 전수 탐색을 제거.

### 결과
**21,000개 Flow 테스트에서 처리량 2,254 flow/s → 120,784 flow/s (약 53.6배 향상).**

| 지표 | 개선 전 | 개선 후 |
|---|---|---|
| 처리량 (21,000 Flow) | 2,254 flow/s | **120,784 flow/s** |
| 병목 원인 | O(n) 전수 탐색 | 탐색 비용 제거 |

## 3. 오탐 튜닝 (ACK_SCAN)

### 증상
정상적인 **RDP 세션의 ACK 통신**을 TCP ACK 스캔으로 오탐해, 같은 시간대 후속 패킷마다 Alert가 반복 생성됐다.

### 원인 진단
ACK 스캔 종합 판정에 쓴 `detection_filter`가 **단순 횟수 기반**이라, 임계값을 넘긴 정상 세션의 연속 ACK를 모두 공격으로 집계했다. 임계 기반 탐지의 전형적인 한계 — **정상 트래픽이 우연히 임계를 넘으면 오탐**이 된다.

### 조치
관제 분석 창에서 해당 `ACK_SCAN` 이벤트 묶음을 **오탐 처리**했다. 오탐률이 50%를 넘어 룰 관리 페이지에 **자동으로 "수정 필요 룰"로 등록**되고, 등록된 IDS 장치에 변경사항을 적용하는 파이프라인을 탔다.
- 개선 방향: 단순 횟수가 아니라 **핸드셰이크 미완료율·목적지 포트 분산** 등 스캔 고유 특성을 결합해 판정(정상 세션과 구분).

### 결과 / 교훈
- **시그니처를 만드는 것보다 오탐을 줄이는 게 실무의 본질**임을 체감. 탐지 룰은 "만들고 끝"이 아니라 **정오탐 판정 → 튜닝 → 재배포**의 운영 사이클을 돈다.

## 4. 중복 Alert 취합

### 증상
같은 공격이 지속되면 동일 Alert가 수십·수백 건씩 쏟아져 분석가가 핵심을 놓친다.

### 조치
반복 Alert를 **공격 유형 · 공격자 · 피해자 · 시간창** 기준으로 묶어 **하나의 Event**로 취합했다. 공격 판정에 실제로 쓰인 패킷과 주변 흐름만 선별 저장해, 판정된 패킷에서 연관 pcap을 역추적할 수 있게 했다.

### 결과
- Alert 폭주 속에서 "하나의 공격 사건" 단위로 조사 가능.
- 원본 데이터 저장 방식도 실측 — **원본 PCAP 저장이 L4 JSONL보다 처리량이 높고 파일 크기가 작아**, 향후 PCAP 순환 저장 + 공격 근거만 장기 보존으로 개선 계획.
